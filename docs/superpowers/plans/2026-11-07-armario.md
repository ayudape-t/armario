# Armario virtual — Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Construir la PWA «armario virtual» del spec: prendas por foto clasificadas por IA, outfits a pedido, agenda, plan gratis/Premium con pago manual por Yape y panel de administrador.

**Architecture:** App React (multi-página con Vite: páginas estáticas públicas + SPA en `/app`) servida por Cloudflare Pages. Supabase da login, Postgres con RLS, almacenamiento privado y 3 funciones Deno. La lógica de las funciones vive en módulos puros (`supabase/functions/_shared/`) con dependencias inyectadas, probados con Vitest (el spec dice «pruebas de Deno»; Vitest prueba la misma lógica sin instalar Deno y con el mismo runner de la app); los `index.ts` de Deno solo conectan. Las reglas de negocio críticas (permisos, límites, pagos) viven en la base de datos y se prueban con pgTAP.

**Tech Stack:** Node 22, TypeScript, React 19.3, react-router 8.5, Vite 8.3, vite-plugin-pwa 2.0, @supabase/supabase-js 2.119, Supabase CLI 3.0 (`npx supabase`), Deno (edge runtime de Supabase), @anthropic-ai/sdk 1.6, zod 4.6, Vitest 5.1, Playwright 1.65, pgTAP.

**Spec:** `docs/superpowers/specs/2026-11-07-armario-design.md` (léelo junto con este plan; las secciones citadas como §N son de ahí).

## Global Constraints

- Todo texto visible para el cliente en español de Perú. Mensajes fijados por el spec, literales: «No parece una prenda», «Solo puedo armar outfits», «No pudimos armar tus outfits, inténtalo de nuevo», «Sin conexión. Inténtalo cuando tengas señal.», «Revisa tu número de operación», «Te quedan X días de Premium gratis», «Tu Premium vence el DD/MM. Renuévalo aquí», «Instala la app en tu celular», «Compartir → Agregar a inicio».
- **El repositorio es público:** ninguna clave, contraseña, número personal ni dato de clientes en el código. Valores de configuración por variables de entorno (`VITE_*` en Cloudflare, secretos en Supabase/GitHub).
- Límites: gratis 50 prendas y 3 pedidos de outfit al día; Premium 1000 prendas y 30 pedidos al día; todos 100 fotos clasificadas al día. Día contado en `America/Lima`.
- Prueba gratis: `premium_hasta = creado_en + interval '7 days'` al registrarse. Aviso de vencimiento: 3 días antes.
- Pases: `1m` «1 mes» 30 días S/9.90 · `3m` «3 meses» 90 días S/24.90 · `12m` «12 meses» 365 días S/79.90.
- Categorías: `arriba`, `abajo`, `vestido`, `calzado`, `abrigo`, `accesorio`. Formalidad de prenda: `formal`, `informal`, `ambas`. Calidez: `ligera`, `media`, `abrigada`.
- Paleta (exacta, 17): negro, blanco, gris, beige, marrón, azul marino, azul, celeste, verde, rojo, rosado, morado, amarillo, naranja, dorado, plateado, estampado.
- Pedido de outfit: `ocasion` 1–80 caracteres; `tema` 0–80; `formalidad` `formal|informal`; `colores` `neutros|llamativos|da_igual`; `clima` `frio|templado|calor|lluvia`. Opciones de ocasión en la UI: trabajo, casual, fiesta de noche, cita, matrimonio, deporte, viaje (o texto libre).
- Largos máximos: `tipo` 40, `titulo` 60, `frase` 200. Outfit válido: 2 a 6 prendas.
- `numero_operacion`: `^[0-9]{6,20}$`, único.
- Fotos: grande 1024 px lado mayor (~150 KB), miniatura 300 px (~20 KB), WebP (JPEG si el navegador no codifica WebP). Bucket `prendas` privado, ≤ 5 MB, solo `image/webp`, `image/jpeg`, `image/png`. Enlaces firmados de 3600 s.
- IA: modelo en variable `IA_MODELO` (por defecto `claude-haiku-5-5`); esfuerzo `low` al clasificar y `medium` en outfits; tiempo máximo de clasificación 20 s; salida estructurada con `client.messages.parse` + `zodOutputFormat`.
- Supabase en región São Paulo. Login con Google y con correo por código de 6 dígitos (OTP, no enlace).

**Entorno local (para quien ejecuta el plan):** iniciar Docker (`dockerd > /tmp/dockerd.log 2>&1 &`), y exportar `SUPABASE_INTERNAL_IMAGE_REGISTRY=docker.io` antes de `npx supabase start` (el registro por defecto está bloqueado en este entorno). Mailpit local en `http://127.0.0.1:54324` recibe los correos con el código.

## Review Focus

1. **Doble toque en «Aprobar»:** aprobar dos veces el mismo pago no debe sumar días dos veces; el segundo intento falla con «el pago ya fue revisado». → prueba en Task 4.
2. **Safari sin WebP:** si `canvas.toBlob('image/webp')` devuelve otro tipo, se sube JPEG con extensión `.jpg`, y la función acepta `.webp` y `.jpg`. → pruebas en Task 5 y Task 6.
3. **Subida múltiple en el borde del límite:** con 49 prendas y 3 fotos a la vez, entra 1 y las otras 2 muestran la ventana de Premium; ninguna se pierde sin aviso. → prueba en Task 6 (49 permite, 50 rechaza) y en Task 11 (UI por foto).
4. **Cambio de día en Lima:** un uso a las 23:59 de ayer en Lima no cuenta para hoy; uno a las 00:01 sí, aunque en UTC sea el mismo día. → prueba en Task 4.
5. **Armario vacío o sin prendas clasificadas al pedir outfit:** responde «Agrega prendas para armar outfits» sin llamar a la IA y sin descontar el pedido. → prueba en Task 8.

      descargarFoto(ruta: string): Promise<Uint8Array>;
      borrarFotos(ruta: string): Promise<void>;           // grande + mini
      insertarPrenda(p: NuevaPrenda): Promise<{ id: string }>;
      clasificarConIA(foto: Uint8Array, tipoMime: string): Promise<z.infer<typeof FichaIA>>; // lanza si falla o tarda > 20 s

    type ResultadoClasificar =
      | { ok: true; prenda_id: string; estado: 'lista' | 'sin_clasificar' }
      | { ok: false; error: 'ruta_invalida' | 'limite_prendas' | 'limite_fotos' | 'no_es_prenda' };
    function procesarClasificacion(deps: DepsClasificar, uid: string, ruta: string): Promise<ResultadoClasificar>;
